# Наблюдаемость Rich Studio

Как студия рассказывает о себе человеку и агенту: журнал, отчёт о состоянии, самоконтроль и уборка. Мерка — один человек, один компьютер, один контейнер. Почему без Prometheus, Loki и Grafana: [решение 0006](decisions/0006-observability-in-process.md).

## Что нужно было решить

1. Видеть, что происходит: запросы к API, вызовы Bot API, фоновые циклы, ошибки. До этого строки `INFO` никуда не попадали, а `uvicorn` писал каждый запрос и каждый `getUpdates` в вывод контейнера без ограничения размера.
2. Журнал не должен расти бесконечно и не должен оказываться в репозитории.
3. Агент в Claude Code должен сам понять, здорова ли студия, и предложить решение, не читая код.
4. Данные, которые копятся от работы (история версий, загрузки, ключи повтора, копии базы), должны иметь предел или хотя бы быть видны.

## Этап 1 (этот PR)

### Журнал

- `app/logs.py`: два выхода. В stderr (то есть `docker compose logs`) короткие строки для человека, в `DATA_DIR/logs/studio.log` строки JSON для агента: `ts`, `level`, `logger`, `msg` и поля события.
- Размер ограничен: файл до `LOG_MAX_MB` (5) и `LOG_FILES` (3) старых копий, итого не больше 20 МБ. `LOG_MAX_MB=0` оставляет только stderr. Вывод контейнера ограничен в `docker-compose.yml`: 3 × 10 МБ.
- Журнал лежит в `DATA_DIR` (`./data` в Docker, `/tmp/rs-data` у `make dev`), то есть вне git: `data/` в `.gitignore`.
- События:

| `event` | Где пишется | Поля |
|---|---|---|
| `http` | middleware в `main.py`, кроме `/healthz`, `/api/health`, `/api/logs`, статики | method, path, status, ms, client (`X-Studio-Client`) |
| `telegram.call`, `telegram.error` | `telegram.client.call`; успешный `getUpdates` не пишется | method, ms, code, chat_id |
| `health.change` | `services/housekeeping.watch` | check, status, action |
| `cleanup`, `backup.daily`, `start`, `stop` | уборка, бэкап, запуск | что сделано |

- Токен вычищается из каждой готовой строки (`logs.scrub`) в обоих выходах, включая трассировки. Текст постов, запросы и тела ответов не пишутся. `httpx` понижен до `WARNING`: его строки с URL дублировали наши.
- Предупреждения `uvicorn.error` (падение запроса с трассировкой) тоже попадают в файл.

### Отчёт о состоянии

`GET /api/health` (и MCP `studio_health`) собирает отчёт из 11 проверок, каждая `ok | warn | fail` с `summary`, подсказкой `action` и `details`. Общий `status` — худший из них, `problems` — короткий список того, что не ok.

| Проверка | Смотрит |
|---|---|
| `database` | версия схемы против кода, число постов |
| `disk` | свободное место в `DATA_DIR` |
| `telegram` | токен, состояние `getUpdates`, итог последнего вызова Bot API |
| `loops` | пульс фоновых циклов: планировщик, события, спецификация, бэкап, уборка |
| `scheduler` | отложенные посты, которые ждут дольше срока |
| `posts` | не ушедшие и пропущенные посты, несработавшие первые комментарии за сутки |
| `sends` | отправки «мог уйти» (`Idempotency-Key` со статусом uncertain) за сутки |
| `spec` | версия спецификации и последняя попытка скачать |
| `backup` | возраст последней ежедневной копии базы |
| `storage` | размер базы, загрузок (и сколько из них не нужно), копий, журнала; число версий постов |
| `log` | ошибки за последний час |

- Счётчики в `app/metrics.py` живут в памяти процесса (с запуска): запросы по классам ответа, вызовы Bot API по методам и исходу, предупреждения и ошибки, последние 30 из них, пульс циклов. На диск не пишутся: после перезапуска история есть в журнале.
- Сломанная проверка сама становится `fail` с текстом исключения, а не ломает отчёт.
- `/healthz` остаётся простой проверкой «жив» для Docker и без ключа API.
- `GET /api/logs?level=&limit=&since=&logger=&q=` (и MCP `studio_logs`) читают хвост журнала с фильтрами, так что агенту не нужен доступ к Docker.

### Самоконтроль и уборка

`services/housekeeping.loop` раз в 5 минут считает отчёт и пишет в журнал каждую смену статуса проверки (`health.change`: `posts: ok → warn: …` и обратно). Так в журнале остаётся хронология: когда сломалось, когда починилось. Раз в час уборка:

- всегда: ключи `Idempotency-Key` старше суток (раньше они удалялись только при новой отправке);
- только по настройке: версии постов сверх `VERSIONS_KEEP` на пост, загрузки, которые ничему не нужны дольше `MEDIA_UNUSED_DAYS` дней. По умолчанию обе выключены: это сделанное человеком, удалять его молча нельзя. Вместо этого `storage` предупреждает, когда ненужные загрузки занимают больше 200 МБ.

Что уже было ограничено раньше: ежедневные копии базы (`BACKUP_KEEP`), ответы кнопок предпросмотров (20), история изменений спецификации (50), временный zip экспорта.

### Сторона агента

- `.claude/skills/studio-health/SKILL.md`: как читать отчёт и журнал, что значит каждая проверка, как решать и чего не делать без согласия человека. Тест сверяет таблицу проверок в skill с `health.CHECKS`.
- `.claude/agents/studio-monitor.md`: субагент только для чтения (GET-запросы и файлы, без Edit/Write). Отвечает коротко: общий статус, что нужно от человека, по строке на проблему с действием.
- Наблюдение во времени: в локальной сессии Claude Code `/loop 30m` с `studio-monitor`. Облачная рутина сюда не подходит: она не видит `localhost` пользователя.

## Этап 2 (предложение, не сделано)

1. Уведомление в личку (`TG_PREVIEW_CHAT`), когда проверка переходит в `fail` или пост стал `missed`/«мог уйти», с ограничением частоты. Это закрывает «узнать вовремя», когда студию никто не открывает.
2. Значок состояния в шапке редактора из `/api/health`.
3. `GET /metrics` в формате Prometheus, только если появится внешний мониторинг (см. 0006).
4. Хук `SessionStart` в `.claude/`, который при запуске Claude Code в папке студии одной строкой говорит, если отчёт не ok.

## Куда добавлять новое

- Новая проверка: функция в `services/health.py`, строка в `CHECKS` и строка в таблице `.claude/skills/studio-health/SKILL.md` (тест сверяет). Проверка только читает.

- Новый фоновый цикл: `metrics.beat("имя", INTERVAL, error)` в конце каждого круга и строка в `health._expected_loops`.
