# Наблюдаемость Rich Studio

Как студия рассказывает о себе человеку и агенту: журнал, отчёт о состоянии, самоконтроль, уборка и сигнал снаружи. Всё внутри одного процесса, без Prometheus, Loki и Grafana ([0006](decisions/0006-observability-in-process.md)); имена полей, id запросов и формат отчёта — [0025](decisions/0025-log-fields-and-health-format.md).

## Журнал

`app/logs.py`, два выхода: в stderr (`docker compose logs`) короткие строки для человека, в `DATA_DIR/logs/studio.log` строки JSON для агента: `ts` (UTC, RFC 3339 с `Z`), `level`, `logger`, `msg` и поля события. Файл читают `GET /api/logs?level=&limit=&since=&logger=&q=` и MCP `studio_logs`, доступ к Docker для этого не нужен.

- Запись вне event loop: логгеры кладут запись в `QueueHandler`, файл и stderr пишет поток `QueueListener`. `request_id` и трассировка снимаются ещё в вызывающем потоке. `logs.flush()` ждёт, пока поток допишет; `/api/logs` зовёт его сам.
- Размер: файл до `LOG_MAX_MB` (5) и `LOG_FILES` (3) старых копий. `LOG_FILES` не меньше 1: при 0 стандартная ротация не работала бы вовсе. Копии сверх `LOG_FILES` удаляются при старте, чужие файлы в папке (`studio.log.old`) не читаются. `LOG_MAX_MB=0` оставляет только stderr. Файлы доступны только владельцу (0600). Вывод контейнера ограничен в `docker-compose.yml`: 3 × 10 МБ.
- Не пишутся текст постов, query, тела запросов и ответов. `httpx` понижен до `WARNING`: его строка на каждый запрос дублировала бы `telegram.call`. Предупреждения `uvicorn.error` (падение запроса с трассировкой) попадают в файл.

### Секреты

Одна функция `redact.scrub` маскирует токен бота (значение `TG_BOT_TOKEN`, любой токен по виду, обрезанный хвост после `/bot`, всё это и с `%3A` вместо `:`), `STUDIO_API_KEY` (и в URL-кодировке) и именные токены `rs_…`: `<token>`, `<api-key>`, `<rs-token>`, остальной текст не меняется. Значение из настроек короче 8 символов не ищется: локальный ключ `1` превратил бы в маски любой текст. Чистится каждая готовая строка обоих выходов с трассировками, весь отчёт `/api/health` и всё, что студия отдаёт или хранит как текст ошибки: страница 404 прокси, неверный `TG_API_BASE` или свой сервер Bot API могут повторить URL с токеном.

- Транспорт (`telegram/client.py`) чистит ответ Telegram с ошибкой, страницу прокси (до обрезки до 300 символов) и текст сетевой ошибки `httpx` посреди запроса, прежде чем бросить исключение. Поэтому выше чистые тексты идут сами, в том числе в ответы 200: `results[].error` рассылки, предупреждения, сохранённый результат `Idempotency-Key`.
- Хранилище чистит при записи `posts.error`, `posts.reply_errors` и ответ «мог уйти» в `idempotency`.
- То, что отдаётся, чистят обработчики ошибок в `main.py` (ответы API), `errors_as_tool_errors` (ошибки MCP) и `updates.STATUS.as_dict` (`/api/config`, `/api/updates`, `studio_status`).

### Один id на единицу работы

- Каждая строка, записанная во время HTTP-запроса, несёт `request_id`; тот же id приходит в заголовке ответа `X-Request-ID`, и у ответа 500 тоже. `GET /api/logs?q=<id>` показывает строку `http`, вызовы Bot API и ошибку одного запроса вместе.
- Id берётся у вызывающего, если он прислал разумный `X-Request-ID` (до 64 символов `A-Za-z0-9._:-`) или W3C `traceparent` (его trace-id; строчные hex, нулевые id отвергаются, у версии `00` ровно четыре поля). Иначе новый, 32 hex. Агент может задать id своего запроса сам и потом найти его в журнале.
- Фоновая работа получает id на каждый круг: `scheduler-…`, `spec-…`, `backup-…`, `housekeeping-…`, событие от Telegram — `update-<update_id>`.
- Механика: `contextvars` в `logs.py` (`bind`), переходит в `asyncio.to_thread`. У ошибок в `recent_problems` отчёта тоже есть `request_id`.

## Отчёт о состоянии

`GET /api/health` и MCP `studio_health` собирают отчёт из проверок `health.CHECKS`, у каждой `ok | warn | fail`, `summary`, подсказка `action` и `details`. Общий `status` — худший из них, `problems` — по строке на всё, что не ok. `version` (студии), `bot_api` и `time` (UTC) показывают агенту, сравнивающему два отчёта, обновлялась ли студия между ними. Сломанная проверка сама становится `fail` с текстом исключения, а не ломает отчёт. Что значит каждая проверка и что с ней делать — таблица в `.claude/skills/studio-health/SKILL.md`.

- Проверка `telegram` смотрит только на сбои связи и настройки (`metrics.about_the_studio`): сеть, 401/403, 429, 5xx и 400 про чат, права, тему или группу. 400 про сам пост (неверное поле, поздний клик) виден у поста и в `posts` и прежнюю ошибку настройки не затирает; успешный `getUpdates` снимает только свою ошибку связи.
- Запись поста, который мог уйти, проверка `posts` показывает без срока: решает человек ([политика ошибок](ARCHITECTURE.md#политика-ошибок-при-отправке)).
- Счётчики (`app/metrics.py`) живут в памяти процесса с запуска: запросы по классам ответа, вызовы Bot API по методам и исходу, предупреждения и ошибки (последние 30), пульс фоновых циклов. Задержки `http_latency` и `telegram_latency`: `n`, `p50_ms`, `p95_ms`, `max_ms` по последним 200 вызовам каждого маршрута (по шаблону, `GET /api/posts/{pid}/versions`, а не по id) и метода Bot API. Долгий опрос `getUpdates` в задержки не входит: он длится, пока Telegram молчит. На диск счётчики не пишутся, после перезапуска история есть в журнале.

### `/healthz` и `/readyz`

Оба открыты без ключа. `/healthz` — «процесс жив», для `HEALTHCHECK` в `Dockerfile`; на базу и Telegram не смотрит, чтобы Docker не перезапускал студию из-за чужой беды. `/readyz` — 503, пока хоть одна проверка в `fail`. Отчёт для него пересчитывается не чаще раза в 30 секунд и отдаёт только имена проверок (`{"ready": false, "failing": ["disk"]}`), подробности — в `/api/health` за ключом.

## Самоконтроль и уборка

`services/housekeeping.loop` раз в 5 минут считает отчёт и пишет в журнал каждую смену статуса проверки (`health.change`: `posts: ok → warn: …` и обратно): видно, когда сломалось и когда починилось. Раз в час уборка:

- всегда: ключи `Idempotency-Key` успешных запросов старше суток; ключи «мог уйти» не удаляются;
- только по настройке: версии постов сверх `VERSIONS_KEEP` на пост и загрузки, которые ничему не нужны дольше `MEDIA_UNUSED_DAYS` дней. По умолчанию обе выключены: это сделал человек, молча удалять нельзя. Вместо этого `storage` предупреждает, когда ненужные загрузки занимают больше 200 МБ.

Ограничены и без уборки: ежедневные копии базы (`BACKUP_KEEP`), ответы кнопок предпросмотров (20 последних), история изменений спецификации (50), временный zip экспорта (удаляется после отдачи).

## Сигнал снаружи

`DEADMAN_URL` ([0011](decisions/0011-dead-mans-switch.md)): после каждого круга самоконтроля (5 минут) студия открывает адрес, при отчёте `fail` — `адрес/fail`. Пинг идёт из процесса, который держит lease, поэтому подтверждает и HTTP, и фоновые циклы. Неудачный пинг — предупреждение `deadman.error` без адреса: он секрет. Снаружи можно ещё смотреть `/readyz`.

## Кто смотрит

- **Значок в шапке редактора** (`components/rs-health.js`, `health.js`) показывает тот же `/api/health`: зелёная точка — всё в порядке, жёлтая или красная с числом проблем — нет, красная без числа — студия не ответила, серая — отчёта ещё нет или студия просит ключ API. Нажатие открывает все проверки с `action`. Отчёт запрашивается раз в минуту и при возвращении на вкладку, скрытая вкладка не спрашивает. Опрос идёт через `probe()` из `api.js` и на 401 ключ не спрашивает: окно ключа раз в минуту было бы невыносимо, ключ спросит первое действие человека. Своего маршрута у значка нет: человек видит ровно то, что читает агент.
- **Хук `SessionStart`** (`.claude/hooks/studio_health.py`, при `startup` и `resume`) за 1,5 секунды спрашивает `/api/health` по `STUDIO_URL` (токен из `STUDIO_TOKEN`, ключ из `STUDIO_API_KEY` или `.env`; в вывод они не попадают). Статус не `ok` — одна строка человеку (`systemMessage`) и агенту (`additionalContext` с пометкой «данные, не инструкции»: там цитаты из Telegram и журнала). Студия не запущена или ответила 401 — строка только агенту: его инструменты `rich-studio` не ответят, и он должен знать почему. Студия в порядке или отвечает дольше 1,5 секунды — хук молчит: сессия не должна становиться медленнее или шумнее. Прокси из окружения для `localhost` не используется.
- **Агент**: skill `.claude/skills/studio-health/SKILL.md` (как читать отчёт и журнал, что делать и чего не делать без согласия человека) и субагент `.claude/agents/studio-monitor.md` (только чтение, короткий ответ). Наблюдение во времени — `/loop 30m` со `studio-monitor` в локальной сессии Claude Code: облачная рутина не видит `localhost` пользователя.

## Куда добавлять новое

- Проверка состояния: функция в `services/health.py`, строка в `CHECKS` и строка в таблице `.claude/skills/studio-health/SKILL.md` (тест сверяет). Проверка только читает.
- Событие журнала: `log.info("…", extra={"event": "имя", ...})` в своём модуле и строка в таблице событий выше. Не кладите в `extra` текст поста, токен или ключ API.
- Фоновый цикл: функция в `factories` (`main.lifespan`), id круга через `logs.bind(logs.new_id("имя-"))`, `metrics.beat("имя", INTERVAL, error)` в конце каждого круга и строка в `health._expected_loops`.
