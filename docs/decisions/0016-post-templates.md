# 0016. Шаблоны постов: поля `{{key}}` только там, где значение остаётся текстом

2026-11-15, задача #93: рубрику (дайджест, анонс) сохранить шаблоном с полями и получать из неё новый черновик в редакторе и через MCP. Идея взята из форка xarleyn/Rich-Studio, код написан заново.

**Решение.** Шаблон — отдельная таблица `post_templates(id, title, payload, fields, version, …)`, а не особый черновик. Поле — `{key, label, type: text | multiline | url, required, default}`. `{{key}}` стоит только в строковых значениях поста; в ключе JSON он не принимается. При заполнении значение всегда остаётся текстом: в HTML (`html` у `rich_message` и у первого комментария) его экранирует `html.escape`, в остальных строках оно уходит обычной строкой JSON (текст блока Telegram не разбирает). Поэтому при сохранении шаблона (422) проверяется, где стоит переменная. В HTML она допустима только в тексте и в значении атрибута в кавычках. Где кончается тег и где значение в кавычках, сервис определяет по правилам токенизатора HTML5, как браузер предпросмотра: пробелы — только пробел, `\t`, `\n`, `\r`, `\f`. Всё, что HTML5 называет ошибкой разбора внутри тега или комментария, в HTML с полями даёт 422: `=` без имени атрибута, кавычка или `<` в имени, кавычка или `=` в значении без кавычек, значение без пробела после него, незакрытые тег, кавычка или комментарий, `<` вне тега, `<!…>` кроме комментария, элементы с сырым текстом (`script`, `style`, `xmp`, `textarea`…). Ошибку разбора браузер и Telegram могут исправить по-разному, и переменная после неё окажется среди атрибутов. Эквивалентность проверяет e2e `40-post-templates.mjs`: настоящий HTML5-парсер Chromium разбирает принятые шаблоны с враждебными значениями, и теги с атрибутами не меняются; на отвергнутых примерах тот же парсер показывает, что значение добавило бы атрибуты. Переменная в имени тега или атрибута, в значении без кавычек и в комментарии отвергается. В `href`/`src` и других атрибутах-ссылках (`srcset`, `xlink:href`, `cite`, `data`, `action`, `formaction`, `poster`, `background`, `ping`) допустимо только поле типа `url`, и только целиком. Поле `url` принимает то же, что `safeUrl` предпросмотра (`http(s)`, `tg`, `mailto`, `tel`, `#якорь`, `/путь`), или файл `upload:имя`. Файл работает только в медиа-полях JSON (`telegram/` переписывает `upload:` в `attach://` только там), поэтому в атрибуте HTML `upload:` не принимается ни по умолчанию, ни при заполнении: в HTML-посте файл лежит в `rich_message.media`, а текст ссылается на него через `tg://photo?id=`. Переменная рядом с `parse_mode` или `entities` (подпись медиа, вопрос опроса) не принимается: Telegram разметил бы значение по ним. Ссылку `upload:` подставляет только поле целиком; если она собирается из частей при заполнении, это тоже 422. У шаблона есть `version`: правка, удаление и заполнение по старой версии получают 409. Заполнение создаёт новый черновик без каналов. Размер результата считается до того, как пост собран (на каждую подстановку прибавляется длина значения), и больше 1 МБ — 413. Остальное в посте не меняется (правило 1 AGENTS.md). Файлы из поста шаблона и из значений по умолчанию считаются нужными: уборка их не трогает, удаление спрашивает подтверждение. В редакторе шаблоны — свёрнутая строка над черновиками: четвёртая вкладка не помещается в боковую колонку 240 px. Строки, которые можно сделать полем, находит обход JSON поста, а не список типов блоков; пары «поле=значение», которые фиксирует спецификация (тип блока, значение enum), полем не предлагаются.

**Почему так.** Подстановка, которая экранирует значение по месту, закрывает класс ошибок «значение стало разметкой» целиком, если места проверены заранее, при сохранении шаблона. Отказ при сохранении понятнее, чем пост, который потом сломается или выйдет не таким. Размер считается заранее, потому что 1 МБ шаблона с полем, повторённым тысячи раз, иначе собрал бы гигабайты.

**Отказались.** От Markdown в v1: как экранировать значение для Markdown Telegram, ни с чем не сверено. Числовые сущности `&#NN;` из форка внутри кода и формул видны буквально, а свой сканер Markdown на Python пришлось бы держать в согласии с разбором Telegram. Поэтому переменная в Markdown — понятный отказ «переведите в визуальный режим или HTML». От шаблона как особого черновика или записи в localStorage: у него своя версия и свои поля, и агенту он нужен через API. От языка шаблонов с условиями и циклами: рубрике нужна подстановка строк, а логика в шаблоне усложнила бы проверку мест. От частичной подстановки в `upload:` и в ссылки (`https://site/{{slug}}`): файл или адрес, собранный из кусков, не видят ни уборка файлов, ни проверка схемы.

**Не сверено с Telegram.** Экранирование `html.escape` даёт `&lt;`, `&gt;`, `&amp;`, `&quot;` и `&#x27;`. По документации Bot API для HTML поддерживаются эти именованные сущности и все числовые. Примера с ними в `tests/telegram_parse/` пока нет.

**Сверено 2026-11-15 и 2026-11-16 (#170, #173).** Всё, что даёт `html.escape` (`&lt; &gt; &amp; &quot; &#x27;`), Telegram разбирает обратно в символы: именованные из таблицы `TG_ENTITIES` (`app/spec/validator.py`), числовые с маленькой x. В адресе ссылки `&quot;` выбрасывает ссылку (`html-href-quot` в `tests/telegram_parse/captured.json`), но в адрес попадает только поле `url` целиком, а оно кавычек не принимает (`_url_problem` в `app/services/templates.py`). Адрес с `&quot;`, написанный в шаблоне руками, проверка поста считает ошибкой.

**Уточнено 2026-11-16 (#178):** правило ссылок действует и в JSON: строка под ключом `url` (ссылка в тексте блока, кнопка, `web_app`) принимает только поле типа `url` целиком, как `href` в HTML; текстовое поле или кусок ссылки (`https://site/{{slug}}`) там дают 422 при сохранении шаблона. Файл `upload:` туда не подставляется, как и в атрибут HTML.

**Уточнено 2026-11-16 (#188):** `callback_data` кнопки поста (под постом или в блоке кнопок), у которой есть ответ в `callbacks`, полем не становится: 422 при сохранении шаблона, если значение с подставленными default совпадает с ключом `callbacks`. Ответ на нажатие ищется по этому ключу, а ключ JSON полем не заполняется, поэтому другое значение оставило бы кнопку без ответа. Отказались от предупреждения в `callbacks.check` о кнопке без ответа после заполнения: ошибку видно только в готовом черновике, а исправлять её надо в шаблоне. Кнопки внутри rich-ответа (`callbacks.<data>.reply`) правило не трогает: на их нажатия студия не отвечает. Окно шаблона повторяет это правило и `_formatted_by` (строка рядом с `parse_mode` или `entities`): такие строки «→ поле» не предлагает, а `callback_data` с ответом показывает с причиной.
