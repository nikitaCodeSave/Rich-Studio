# 0018. Визуальный пост в HTML по кнопке, а не синхронизация вкладок

2026-11-15, задача #94, после разбора форка xarleyn/Rich-Studio.

**Решение.** В визуальном режиме есть кнопка «В HTML». Она переводит блоки в rich HTML Telegram и кладёт результат во вкладку HTML. Если там уже есть свой текст, сначала спрашивает в диалоге студии. Остальные вкладки сами не меняются: у каждого режима свой текст, как и раньше. Обратное направление уже есть: «В визуальный» после «Мне в личку» берёт блоки, которые сделал из поста Telegram.

Что во что переводится, записано руками в `app/static/js/html-export.js`, как отрисовка в `render.js`, по разделу [Rich HTML style](https://core.telegram.org/bots/api#rich-html-style). Таблица — это `BLOCK_FIELDS` и `INLINE_FIELDS`: тип и поля, которые он переносит. Каких типов спецификации в ней нет, перечисляет `spec/coverage.py`, так же как пробелы подписей и предпросмотра. Их видно в окне спецификации, а `tests/test_spec_coverage.py` с ними красный. Новое поле у типа, который в таблице уже есть, учёт не ловит. Потери и тогда нет: кнопка откажет с перечнем при первом посте с этим полем, но узнают о нём от человека, а не из теста.

**Без потерь.** Перевод идёт по копиям и отказывает целиком, если что-то из поста в HTML не попадёт. Тогда диалог перечисляет, что и где, а вкладка HTML остаётся как была. Отказ дают: тип или поле, которых нет в таблице (например, `width`/`height` у карты, `bot_username` у кнопки входа: таких атрибутов в HTML нет), и значение, которое Telegram в HTML прочитает иначе. Так бывает с @упоминанием, #хэштегом и другими элементами, которые Telegram находит в тексте сам: при `skip_entity_detection` он их не найдёт, а без него найдёт только по их собственному тексту. Так же отказ дают дата без текста, которую Telegram выбрасывает, и ссылка `mailto:`/`tel:`/`#…`, которую он прочитает как почту, телефон или якорь. Тип, который в HTML не записать совсем, стоит в таблице без полей (`null`), а причина записана в `NO_HTML`. Сейчас таких нет. Адрес TON из Bot API 10.4 был таким, пока не проверили: тега для него нет, но Telegram находит его в тексте HTML сам (`html-detected-card-ton` в `tests/telegram_parse/captured.json`), поэтому он пишется своим текстом, как @упоминание. Адрес ссылки и кнопки с `"` пишется с `%22`: с `&quot;` Telegram ссылку выбрасывает (`html-href-quot`), а пост с такой кнопкой отклоняет. Номер карты Telegram находит в тексте HTML только без пробелов (замер к issue #170: `4242424242424242` да, `4242 4242 4242 4242` нет). Перевод не убирает пробелы сам: тогда текст в HTML читался бы иначе, чем в блоках. Он пишет номер так, как его записал автор, и после перевода предупреждает, что номер с пробелами останется текстом. Готовый HTML разбирается тем же кодом, что предпросмотр (`RichRender.outline`), и сравнивается с блоками. Если они разошлись, это тоже отказ, и диалог показывает место расхождения. Outline сверяет структуру и текст, но не значения атрибутов: адрес ссылки, `rowspan`, точку и масштаб карты, `unix` и `format` у `<tg-time>`, `emoji-id`. Их проверяют отдельные строковые проверки в `tests/html_export.mjs`. Медиа из блоков попадают в `rich_message.media` с id, которые не совпадают с уже занятыми; запись с тем же файлом используется снова. В тексте медиа ссылаются только по схемам из документации: `tg://photo`, `tg://video`, `tg://document` и `tg://audio`. Поэтому анимация пишется как `<video src="tg://video?id=…">`, а голосовое как `<audio src="tg://audio?id=…">`, теги из описаний `InputRichBlockAnimation` и `InputRichBlockVoiceNote`. Вид файла хранит запись в `media` (`InputMediaAnimation`, `InputMediaVoiceNote`). Предпросмотр определяет вид такого файла по ссылке, поэтому для сверки анимация считается видео, а голосовое аудио.

Пробельные символы Telegram читает в HTML так же, как браузер: несколько пробелов подряд, табуляция и отступ после переноса строки становятся одним пробелом, а пробелы в начале абзаца пропадают (в `captured.json`, `example-post-extras`). Outline этого не различает. Отказ здесь был бы слишком строгим: текст остаётся, пропадают только лишние пробелы. Поэтому экспорт проходит, а предупреждение называет места (в коде `<pre>` пробелы сохраняются, там его нет).

Умолчания таблицы взяты у Telegram: у `<th>` выравнивание по центру, у `<td>` по левому краю, по вертикали посередине (кейс `html-table-plain` в `captured.json`). Атрибут пишется, только когда значение отличается от умолчания. У ячеек редактора `valign` по умолчанию `top`, поэтому в HTML он пишется явно.

**Как проверено.** `npm run test:export` (в `make check`, в CI в job `e2e`, где есть Python студии) берёт блоки, которые настоящий Telegram сделал из каждого примера `tests/telegram_parse/captured.json`. Их переводит в отправляемые `spec/convert.py`, как для «В визуальный», затем они идут в HTML, и HTML должен дать тот же outline, что блоки Telegram. Тот же тест прогоняет пост со всеми блоками и элементами спецификации и проверяет отказы. Как разберёт этот HTML сам Telegram, по-прежнему показывает «Мне в личку» со сверкой.

**Отказались.** От автоматической синхронизации вкладок при переключении: она молча затирала бы текст, который человек писал руками, и выбирала бы, какая вкладка главная. От своего разбора HTML для сверки: чужой разбор, сверенный только с нашим предпросмотром, ничего не доказывает. Сверка идёт через `render.js`, а его правила записаны с настоящего Telegram (`npm run test:parity`). От жёсткого списка блоков вне учёта `test_spec_coverage.py`: новый блок спецификации должен сразу попадать в список пробелов, а не теряться при переводе.
