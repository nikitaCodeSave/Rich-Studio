# 0009. Именные токены с уровнями и cookie-сессия, а не пользователи и OAuth

2026-10-28, ревью к продакшну (этап 4), сценарий «свой сервер для Никиты и его агентов».

**Решение.** Доступ — это именные токены, у каждого один уровень: `read` < `draft` < `publish` < `admin`. Выдаёт, показывает и отзывает их команда `cli.py token` (`make token`). Токен печатается один раз, в базе хранится только SHA-256 хэш. `STUDIO_API_KEY` остался ключом уровня `admin`. Без ключа и без токенов студия открыта, как раньше на `127.0.0.1`. Отзыв последнего токена студию не открывает. Имя токена пишется в историю постов (`actor`), заголовок `X-Studio-Client` его только уточняет. Редактор меняет ключ или токен на серверную сессию в cookie `HttpOnly; SameSite=Strict` (`Secure` по HTTPS), сессии лежат в SQLite. `/api/raw` и скачивание бэкапа доступны только `admin`, `RAW_API=off` выключает raw совсем.

**Почему.** Один общий ключ нельзя отозвать у одного агента и нельзя ограничить «только черновики». К тому же «кто отправил» записывался со слов клиента. Уровни вместо набора прав покрывают все случаи этой студии: агент-черновик, агент-публикатор, человек-админ. Хэш SHA-256 без соли достаточен, потому что токен — 32 случайных байта, а не пароль. Ключ в cookie, которую ставил JS, уносился любым XSS. Сессия `HttpOnly` скрипту недоступна, а `SameSite=Strict` вместе с проверкой Origin закрывает CSRF.

**Отказались.** От пользователей с паролями и от OAuth/OIDC внутри студии: человек один, а вход извне надёжнее закрыть прокси (Tailscale, Cloudflare Access) перед студией, это этап 5. От JWT: токены живут долго, их нужно отзывать, а для этого всё равно нужна таблица. От отдельного экрана токенов в редакторе: кто может открыть редактор, не должен сам выдавать себе `admin`.
