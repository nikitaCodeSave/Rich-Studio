# 0012. Скачивание по ссылке идёт через системный прокси, как запросы к Telegram

2026-10-28, проверка `upload_media` и `/api/media/fetch` на настоящем https (облачная сессия с выходом в интернет).

**Решение.** Если для ссылки задан прокси (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, с исключениями из `NO_PROXY`), скачивание идёт через него, как и запросы к Bot API. Без прокси всё как раньше: соединение с адресом, который студия проверила (только публичные, на каждом редиректе), имя остаётся в `Host` и в проверке сертификата. Сертификаты берутся из `SSL_CERT_FILE`/`SSL_CERT_DIR`, если они заданы, иначе из certifi. В `User-Agent` студия называет себя (`RichStudio/<версия>`).

**Почему.** Раньше скачивание игнорировало окружение целиком (`trust_env=False`): в сети, где наружу можно только через прокси или где прокси подменяет сертификаты, любая https-ссылка падала с `ConnectError`, хотя посты в Telegram уходили. На живой проверке так и вышло. Отдельно Wikimedia и другие хостинги отвечают 403 на `python-httpx` в `User-Agent`.

**Цена.** Через прокси нельзя закрепить соединение за проверенным адресом: прокси сам разрешает имя (защита от DNS rebinding работает только без прокси). Поэтому до всякого разрешения студия отклоняет внутренние имена: без точки (`intranet`, `localhost`) и с локальными суффиксами (`.local`, `.localhost`, `.internal`, `.lan`, `.home.arpa`, `.corp` и похожие). Адреса из локальной сети отклоняются, если имя разрешается на месте; публичное на вид имя, которое на месте не разрешается, уходит прокси (сеть, где DNS есть только у прокси). Прокси, который пускает во внутреннюю сеть по публичному на вид имени, — настройка этой сети, а не студии.

**Отказались.** От отдельной настройки «прокси для скачивания»: хватает стандартных переменных и `NO_PROXY`. От `verify=False` и своего списка сертификатов.
