# 0022. Предпросмотр по Telegram Desktop: код-блок без подсветки синтаксиса, вид файла `tg://` по записи в `media`, адрес TON по контрольной сумме

2026-11-16, issue #172: предпросмотр сверен с Telegram Desktop в тёмной и светлой теме, а правила для адреса TON проверены на настоящем Telegram.

**Решение.** Код-блок нарисован как в Telegram Desktop: полоса слева, шапка и значок копирования справа. Значок копирует код. В шапке язык, а у блока без языка подпись «копировать», как у клиента. Подсветки синтаксиса нет: код одного цвета, того, каким клиент пишет код без подсветки (голубовато-серый, а не цвет текста). Цвета обеих тем сверены со скриншотами клиента 2026-11-16 и записаны в `tg.css` с той же пометкой. Шапку пишет CSS из `data-lang`, поэтому в текст поста она не попадает: outline, история правок и диалог ответа видят только код.

**Почему без подсветки.** Взвесили разбор из уже вендоренного набора Lezer ([0017](0017-codemirror-vendored-modules.md)), он не требует новой зависимости.

- Языки. В наборе есть грамматики JavaScript и TypeScript, JSON, CSS, HTML и Markdown. Python из самого issue в нём нет, как и почти всех языков, которые подсвечивает Telegram. Каждая новая грамматика (`@lezer/python` и другие) — новая рантайм-зависимость.
- Вес. `render.js` весит 51 КБ (17 КБ gzip). Подсветка одного JavaScript требует `@lezer/common`, `lr`, `highlight` и `javascript`: 77 КБ gzip, в 4,5 раза больше всего предпросмотра. С CSS, HTML, JSON и Markdown выходит около 115 КБ gzip.
- Где грузится. `render.js` — классический скрипт, его загружают редактор, страница `/render` и MCP-приложение (`app/mcp_tools/preview_app.py`). В MCP-приложении всё встроено в один HTML, а сети нет. Модули Lezer с импортами туда без сборщика не встроить ([0001](0001-no-bundler.md)), поэтому в чате Claude подсветки не было бы, и предпросмотр различался бы от места к месту. В редакторе и на `/render` модули пришлось бы грузить через `import()` из каталога с хешем. Путь к нему знает только `codemirror.js`, а он тянет весь набор (около 380 КБ gzip). Отдельный вход для подсветки — это правка `scripts/vendor_codemirror.mjs`.
- Сходство. Цвета клиента пришлось бы подбирать под каждую тему руками. Проверить их можно только глазами: `npm run test:parity` сравнивает структуру и текст, а не цвет.

Итог: подсветка вышла бы частичной (без языка из issue), тяжёлой и разной в разных местах. Без неё предпросмотр показывает то же устройство блока, что клиент, а цвета кода автор видит в Telegram после «Мне в личку».

**Вид файла `tg://`.** В HTML и Markdown документированы только ссылки `tg://photo`, `video`, `audio` и `document`. Поэтому GIF (`InputMediaAnimation`) приходит как `tg://video`, а голосовое (`InputMediaVoiceNote`) как `tg://audio`. Telegram рисует файл по его записи в `media`: GIF играет сам по кругу, с меткой «GIF» и без кнопок. Предпросмотр теперь тоже берёт вид файла из записи, а по ссылке только тогда, когда записи нет. Файл `.gif` рисуется в `<img>` (в `<video>` GIF не играет), анимация MP4 — в `<video muted loop autoplay playsinline>` без `controls`. Это заменяет фразу из [0018](0018-html-export-on-request.md) «предпросмотр определяет вид такого файла по ссылке»: «В HTML» больше не выдаёт анимацию за видео при сверке.

**Адрес TON.** Telegram сам находит адрес в тексте поста: в HTML, в Markdown и в строках блоков (замер: `{"type":"paragraph","text":"адрес EQAA…AM9c конец"}` возвращается с `ton_address`). При `skip_entity_detection` не находит нигде. Находит он только адрес с верной контрольной суммой: `EQAA…AM9d` и `EQCD39…qB2X` остаются текстом. Это user-friendly адрес: 48 символов base64url или base64, то есть 36 байт: флаги, workchain, 32 байта хеша и CRC16-XMODEM (многочлен 0x1021, начальное значение 0) первых 34 байт, big-endian. Предпросмотр проверяет это одной функцией `RichRender.isTonAddress`, ей же «В HTML» проверяет текст `ton_address`. Различает ли Telegram base64 (`+/`) и base64url (`-_`), не замерено, поэтому принимаем то, что принимает формат: оба алфавита, но не смесь двух. Найденными видели только адреса `EQ…` и `UQ…` (workchain 0), и предпросмотр ищет только их. Случай `html-ton-checksum` в `tests/telegram_parse/cases.json` проверяет сумму, оба алфавита и адреса `Ef…` (masterchain) и `kQ…` (testnet). После съёмки его сверяет `npm run test:parity`. Если Telegram найдёт `Ef…` или `kQ…`, нужно расширить `TON_START` в `render.js`.

**Отказались.** От подсветки разбором Lezer, причины выше. От своего токенизатора на регулярных выражениях (ключевые слова, строки, комментарии): на каждый язык нужны свои правила, и он ошибался бы там, где Telegram прав. От Prism, highlight.js и подобных библиотек: это новая рантайм-зависимость, а её без обсуждения не добавляют (`AGENTS.md`). От поиска адреса TON только по виду, без контрольной суммы: тогда предпросмотр выделял бы опечатки, которые Telegram оставит текстом.
