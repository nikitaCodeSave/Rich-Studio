# 0015. Пост из Telegram в черновик пересылкой боту

2026-11-15, задача #92 после разбора форка xarleyn/Rich-Studio (код форка не переносился).

**Решение.** Владелец пересылает боту пост, свой или чужой, и получает черновик с тем же оформлением. Пересылку студия видит в том же цикле `getUpdates`, который работает под lease ([0007](0007-one-process-lease.md)): одна ветка в `services/updates.handle_update`, без нового фонового цикла, маршрута и инструмента MCP. Принимается только сообщение в личном чате с ботом от аккаунта из `TG_PREVIEW_CHAT` (там числовой id человека), не от бота, и только пересылка (`forward_origin`) или копия rich-поста. Остальное, как и раньше, молча пропускается. Rich-пост переводится в отправляемые блоки (`spec.to_input_blocks`, как в сверке предпросмотра). Обычный пост собирается из `text`/`caption` и entities со смещениями в UTF-16 (`spec/entities.py`): тип entity сопоставляется с типом RichText или InputRichBlock по имени из спецификации, жёсткий список только для типов, которые Telegram находит в тексте сам, и для `text_link` → `url`. Медиа остаются file_id: они годятся тому же боту, ничего не скачивается и не загружается. Кнопки-ссылки остаются, callback-кнопки снимаются: на них отвечал бот исходного поста. Альбом приходит сообщением на каждый элемент и собирается в один черновик (коллаж для фото и видео). Откуда пост, записано в `_studio.source`, что не перенеслось — в `_studio.warnings`; в отправляемый пост это не попадает. Каналов у черновика нет. Ответ — реакция ✍ на пересланное сообщение, а если черновик не сделан, одна строка с причиной (защищённое содержимое, нечего перенести, ошибка студии).

**Почему.** Бот уже получает сообщение целиком: текст, entities, file_id, а rich-пост, возможно, и блоками. Это единственный путь без новой зависимости и без нового секрета. Отправитель один (`TG_PREVIEW_CHAT`), поэтому не нужно связывать пересылку с запросом из редактора: пересылка сама и есть запрос.

**Отказались.**
- MTProto (Telethon), как в форке. Новая рантайм-зависимость, `api_id`/`api_hash` и сессия пользовательского аккаунта: этот секрет сильнее токена бота и читает все чаты владельца. Плюс вход по коду, хранение сессии и ограничения частоты. Импорт по ссылке и весь альбом одним запросом этого не окупают.
- Веб-виджет `t.me/<канал>/<id>?embed=1`. Только публичные каналы, разбор HTML без контракта, вместо rich-поста форк получал заглушку, медиа пришлось бы скачивать.
- Одноразовые запросы `/start import_<id>` и «входящие» из форка. Они нужны, когда боту пишут разные люди; у нас пишет один.
- Отчёт сообщением о каждом импорте. Владелец не хочет сообщений бота в личке, поэтому успех — только реакция.

**Не проверено.** Кладёт ли Telegram `rich_message` в пересланное боту сообщение, неизвестно: форк проверял это только на подставном Telegram. Обработаны оба варианта (блоки из `rich_message` или текст с entities). Фикстура `tests/forward_import/rich_channel_post.json` собрана по `app/bundled/api.json`, настоящий update пересылки кладётся рядом, и `tests/test_forward_import.py` проверяет каждый файл в этой папке.
