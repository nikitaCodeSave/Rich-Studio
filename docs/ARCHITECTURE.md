# Как устроен код Rich Studio

Правило слоёв: **api / mcp_tools → services → telegram / store / spec**. Стрелки идут только вниз.

| Папка / файл | Что делает | Чего не делает |
|---|---|---|
| `app/cli.py` | токены доступа из командной строки (`make token`) | экрана для токенов в редакторе нет намеренно |
| `app/main.py` | `create_app()`: middleware, обработчики ошибок, роутеры, фоновые циклы | логики нет |
| `app/settings.py` | все переменные окружения в одном `Settings`; модули вызывают `settings.get()` в момент использования; проверка при старте (`SettingsError` со всеми ошибками сразу), секреты из `*_FILE`, правила `STUDIO_MODE=server` (`https://` в `STUDIO_URL`, токен бота, `STUDIO_API_KEY` не короче `SERVER_KEY_MIN` = 32 символов, иначе студия не стартует; без ключа вход только по именным токенам, их наличие проверяет `main.py` при старте) | не читает env при импорте других модулей |
| `app/security.py` | Host, CSRF, Content-Type, CSP; кто спрашивает (`Principal`: именной токен, `STUDIO_API_KEY` или cookie сессии редактора) и уровень по методу запроса (GET — `read`, остальное — `draft`) | уровни выше `draft` проверяют сами маршруты (`api.deps.need`) и инструменты MCP (`mcp_tools.common.level_of`) |
| `app/logs.py` | журнал: stderr для человека, JSON с ротацией в `DATA_DIR/logs` для агента, `request_id` на каждой строке (`bind`), вычистка секретов (`redact.scrub`), чтение с фильтрами | |

| `app/metrics.py` | счётчики, задержки p50/p95 и пульс фоновых циклов в памяти процесса; его можно звать из любого слоя | не пишет на диск |
| `app/errors.py` | `StudioError` (400), `NotFound`, `Invalid` (422), `Upstream` (502), `MayHaveGone` (502, «мог уйти»), `Unrecorded` (502, подкласс `MayHaveGone`: пост в канале, студия не смогла его записать); `telegram.TelegramError` с кодом 400 → 422, прочие → 502 | |
| `app/models.py` | тела запросов (pydantic), описания полей на русском для /docs | |
| `app/api/*.py` | роутеры: разобрать запрос → вызвать сервис → вернуть результат | не ходят в Telegram напрямую, кроме `raw` (проверка канала идёт через `services.channels`) |
| `app/mcp_tools/` | MCP-сервер на `/mcp`: курированные инструменты для агентов поверх сервисов, тот же guard и ключ API | не дублирует логику сервисов; удаление постов и `/api/raw` сюда не выносятся; страница предпросмотра `ui://` собирается из `static/` (`preview_app.py`), а не пишется отдельно |
| `app/services/kinds.py` | типы сообщений (`rich`, `poll`, `live_photo`, `paid_media`): метод Bot API, где лежат параметры, подписи, можно ли заменить, где кнопки, проверка перед отправкой; описание для редактора в `/api/config` ([0013](decisions/0013-message-kinds-registry.md)) | тип не угадывается по содержимому: его берут из `posts.kind` |
| `app/services/publisher.py` | отправка (метод по типу из `kinds`), шаги после отправки, рассылка в несколько каналов, валидация, время; подтверждения отправок, которые база не приняла (`unrecorded`, дозапись `write_unrecorded`) | не импортирует FastAPI |
| `app/services/posts.py` | что можно сделать с постом: опубликовать, предпросмотр, отложить, заменить, закрепить, кнопки, удалить; опросы, Live Photo и платный контент отдельными сообщениями (`send_kind`) | |
| `app/services/channels.py` | каналы: название, форум и темы, права бота (из `getChat`/`getChatMember` при проверке); темы из событий `forum_topic_created`/`edited` | Telegram спрашивается только при проверке |
| `app/services/scheduler.py` | отложенные посты | |
| `app/services/loops.py` | фоновые циклы под lease в SQLite: их ведёт один процесс, второй ждёт в резерве; остановка без обрыва отправок | |
| `app/services/updates.py` | getUpdates: нажатия, первый комментарий, реакции, опросы, вступления по ссылкам, предложенные посты и их исходы, пересылки владельца; `STATUS` | |
| `app/services/forward_import.py` | пост, который владелец (`TG_PREVIEW_CHAT`) переслал боту, становится черновиком: rich-блоки или текст с entities, медиа по file_id, источник и предупреждения в `_studio`; ответ — реакция или одна строка отказа ([0015](decisions/0015-forward-import.md)) | ничего не публикует; чужие сообщения и обычные сообщения владельца молча пропускает |
| `app/services/invite_links.py` | именные пригласительные ссылки и платная подписка (create/edit/revoke в Telegram), счётчики вступлений и заявок из `chat_member` / `chat_join_request` | Telegram эти счётчики боту не даёт: только то, что студия увидела сама |
| `app/services/suggested_posts.py` | предложенные посты из личных сообщений канала: что пришло (`suggested_post_info`), принять (`approveSuggestedPost`) или отклонить, исходы из служебных сообщений | публикует принятый пост Telegram, а не студия: в `posts` он не попадает. Решение занимает запись (`pending` → `approving`/`declining`) до запроса: второй клик не уходит, при отказе Telegram запись возвращается, при «могло дойти» ждёт служебного сообщения |

| `app/services/media.py` | имена загрузок, путь внутри папки media, загрузка по ссылке (только публичные адреса, каждый редирект проверяется; через системный прокси, если он задан, ADR 0012), `used` и удаление ненужных файлов | |

| `app/services/listing.py` | как пост выглядит в списках: первая строка, миниатюра, ссылка t.me, подписи кнопок к нажатиям | только читает |

| `app/services/backup.py` | бэкап: zip с базой и файлами, ежедневная копия базы | |

| `app/static/js/` | редактор: ES-модули без сборки, вход `main.js`; общее состояние в `state.js`; вкладки исходника — CodeMirror поверх textarea (`code-editor.js`, подсказки в `completion.js`) | не пишет пользовательский HTML в `innerHTML` (это запрещает ESLint); имён полей Bot API в подсказках нет, они из `/api/spec` |
| `app/static/render.js` | предпросмотр поста, очистка HTML/Markdown (`sanitize`), разбор HTML/Markdown по правилам Telegram, `outline` для сверки | правила разбора меняются только вместе с примером в `tests/telegram_parse/`, записанным с настоящего Telegram |

## Сервер

`deploy/`: студия в образе из GHCR (uid 10001, read-only), Caddy с HTTPS, Litestream с копией базы в S3. Образ собирает `.github/workflows/image.yml` по ручному запуску или тегу `v*`, пакеты из `requirements.lock` с хэшами. Что образ стартует без сети, останавливается по `docker stop` с кодом 0 в пределах `stop_grace_period` и сохраняет данные после перезапуска, проверяет `scripts/image_smoke.sh` (CI `ci.yml`, job `docker`). Восстановление из реплики проверяет `scripts/restore_check.sh` (CI `restore.yml`, ежедневно). Решение: [0010](decisions/0010-server-image-and-pinned-spec.md).

## Политика ошибок при отправке

1. Строка поста пишется со статусом `sending` **до** вызова Telegram (и для немедленной отправки, и для отложенной). Если процесс умрёт между ответом Telegram и записью, строка останется, и следующий старт пометит её «мог уйти». Не получилось записать строку — в Telegram ничего не уходит. Отправка прошла → пост записан как `sent`. Не получилось записать `sent` (диск полон, база только для чтения): пост в канале, и ответ это говорит — `Unrecorded`, 502 «опубликован, студия не смогла записать — не публикуйте повторно» с `chat_id` и `message_id`, а в рассылке канал получает `ok: true, unrecorded: true` (`publisher.unrecorded_send`); `message_id` уходит в журнал (ERROR `send.unrecorded`), а подтверждение остаётся в памяти процесса (`publisher.unrecorded`) и дописывается (`store.confirm_sent`) перед следующей отправкой, проходом планировщика, восстановлением `sending` и при остановке; закреп, комментарий и опрос после такого поста не делаются, пока строка в `sending`, проверка `posts` в `/api/health` её показывает с `message_id` (`details.unrecorded`), а `sends` не советует новый ключ ([0019](decisions/0019-unrecorded-send.md)). Если пост уже ушёл в один канал рассылки, а строку `sending` для следующего записать не удалось, этот канал получает `ok: false` «не отправлено» (в Telegram ничего не уходит), рассылка идёт дальше, и ответ всё равно называет, где пост есть; если не ушло ещё никуда, запрос падает как есть. Всё, что после записи (прежние отказы черновика, закреп, комментарий, опрос `poll_after`, чтение записи, названия каналов, ответ для `Idempotency-Key`), только добавляет предупреждения: сбой любого из этих шагов не превращает 200 в ошибку. Планировщик идёт дальше по очереди, даже если исход одного поста не записался (и `sent` тоже), а первую такую ошибку отдаёт пульсу цикла. Опрос после поста — отдельная строка `kind=poll`, и пишется она как пост: `sending` до запроса, запрос в `in_flight`; строку записать не удалось — опрос не уходит (предупреждение), база не приняла `sent` — `unrecorded` и дозапись, как у поста; при сетевой ошибке, остановке или падении посреди запроса — «мог уйти» с признаком, повтора нет. Первый комментарий отправляется так же: `comment_status='sending'` до запроса (`store.claim_comment`, только если он ещё `waiting`), запрос в `in_flight` по id поста, поэтому остановка ждёт и его (у одного id бывает два владельца — планировщик, пока делает закреп и опрос, и getUpdates с комментарием: `publisher.InFlight` считает владельцев, и закончивший первым не снимает id у другого); оборванный остановкой (`CancelledError`) или сетью комментарий — `failed` с «мог уйти» в тексте, оставленный падением `sending` восстановление `sending` помечает так же, а не «пересылка не пришла» через сутки; повтора нет (update уже подтверждён). Причина сбоя комментария дописывается к `error` поста, а не заменяет его, момент сбоя — `comment_failed_at`. Предупреждения отложенного поста после отправки (закреп, опрос) планировщик тоже дописывает одним `UPDATE` (`store.add_error`): сбой комментария, записанный, пока шли эти шаги, они не затирают. `comment_status='sending'` в списке постов (`listing`) идёт с `comment_in_flight`: `true` — запрос идёт сейчас (id в `in_flight`), `false` — комментарий не подтверждён, его никто больше не отправляет (например, база не приняла `sent` — `send.unrecorded`, или не записался сбой — «could not record the failed first comment»), `null` — процесс в резерве (`loops.STATE.role == 'standby'`): комментарии отправляет держатель lease, отсюда не видно; редактор подписывает их «отправляется», «не подтверждён, мог уйти; не публикуйте заново» и «отправляется или не подтверждён». Неточность: пока планировщик держит тот же id (закреп и `poll_after`, с ожиданиями 429 — до пары минут), `in_flight` не отличает его от комментария, и неподтверждённый комментарий это время выглядит как `true`; отдельный учёт комментариев в `updates._send_comment` — отдельная задача.
2. Сетевая ошибка во время отправки, ответ 5xx или страница ошибки шлюза (`telegram.NoAnswer`) → «пост мог уйти, проверьте канал». Автоматического повтора нет. Повторять можно только то, что точно не ушло: `telegram.Unreachable` (соединение не установлено) и 429; планировщик возвращает такой пост в очередь (`retry_at`). Отложенный пост, опоздавший больше `SCHEDULE_LATE_MIN` (сервис был выключен), не отправляется, а получает статус `missed`. Планировщик идёт по очереди, прочитанной в начале прохода, и ждёт каждую отправку, поэтому оба его решения — одним `UPDATE` с условием: `missed` ставится, только если пост всё ещё ждёт с прочитанным `scheduled_at` (`store.mark_missed`), а берёт он пост, только если время пришло по строке, как она есть сейчас (`store.claim_post`). Перенос или отмена, успевшие до того, как планировщик взял этот пост, побеждают; взятый (`sending`) пост перенести или отменить уже нельзя, студия отвечает 400 «пост в статусе sending».
3. Один канал упал → остальные всё равно отправляются; ответ 200, а `results[].ok` говорит, куда не ушло. Не ушло ни в один канал → ошибка, а не 200: так же для опроса, Live Photo и платного контента. Неудачная отправка (отказ Telegram или «мог уйти») записывается постом со статусом `failed` и текстом ошибки: её видно во вкладке «Посты» и в `list_posts`. Запись «мог уйти» (сетевая ошибка или ответ 5xx, остановка или падение посреди отправки, в том числе опрос после поста) несёт признак `posts.outcome_unknown`: его ставят `store.mark_outcome_unknown` и восстановление `sending`, текст ошибки для этого не читается. Первому комментарию признак не ставится: сам пост в канале, а «решить» запись с признаком значит удалить её (`DELETE`), что для опубликованного поста удаляет его из канала; сбой комментария `/api/health` показывает сутки от `comment_failed_at`, сколько бы студия ни простояла до него. Успешная отправка того же черновика в тот же канал убирает его прежние отказы, а записи с признаком остаются: в канале может быть дубль, и проверка `posts` в `/api/health` показывает их без срока. `DELETE` убирает неудачную запись вручную; для записи с признаком это и есть «решено»: человек проверил канал. Отказ Telegram с кодом 400 отдаётся как 422 (запрос плохой, повтор не поможет), остальные ошибки Telegram как 502.
4. Предпросмотр уходит только в `TG_PREVIEW_CHAT` или в явно указанный chat_id, никогда в канал по умолчанию. Публикация без chat_id уходит в каналы черновика (`drafts.chat_ids`), а если их нет, в канал по умолчанию.
5. `Idempotency-Key` (`services/idempotency.py`, таблица `idempotency`): повтор с тем же ключом возвращает первый результат; если первая попытка закончилась `MayHaveGone`, повтор получает ту же ошибку и подсказку отправить с новым ключом, а после `Unrecorded` — тот же ответ «не публикуйте повторно» без подсказки про новый ключ; исход, который база не приняла, держится в памяти (`idempotency.unwritten`), отвечает на повтор оттуда и записывается при следующем запросе, который публикует, проходе планировщика, взятии lease или остановке; заголовок ответа на повтор после `Unrecorded` говорит, как с записью сейчас: ещё допишется, уже дописана или потеряна с перезапуском («Исход неизвестен»); если ничего не ушло, ключ освобождается. Через сутки уборка забывает только успешные ключи (`done`). Ключ, после которого пост мог уйти (`uncertain` или `pending`, оставленный падением), не истекает и не снимается: повтор с ним в любой срок отвечает «мог уйти». Таких ключей по одному на обрыв сети или падение посреди отправки, предела у таблицы для них нет. Проверка `sends` в `/api/health` показывает ключи `uncertain` только первые сутки, иначе один обрыв держал бы её в warn навсегда; `pending` после падения в `sends` не попадает, его видно в `posts`: строка `sending` после перезапуска становится `failed` с признаком `outcome_unknown` и остаётся там, пока её не уберут. Подсказка в ответе зависит от действия: для поста и опроса — проверить канал вместе с пользователем и отправить с новым ключом, для отложенного — проверить список постов, для одобрения предложенного поста новый ключ не поможет, пока человек не нажмёт «Решить снова».
6. Замена опубликованного поста (`posts.after_edit`) меняет в записи только текст и кнопки; ответы на кнопки и первый комментарий остаются, если новый пост не принёс свои. «message is not modified» от Telegram не ошибка.
7. Каждая замена поста через студию (`posts.edit`, `posts.edit_message`, `posts.set_buttons`) сначала кладёт прежнее содержимое в `post_versions`. Отложенный и пропущенный пост заменяется только пока он ждёт (`status in ('scheduled', 'missed')` в том же `UPDATE`): взятый планировщиком уходит с тем, что было. Редактор передаёт `post_version` прочитанного поста, при 409 показывает, что пост изменили, и заменяет только после подтверждения.
8. Кто отправил пост, пишется в `posts.actor` из заголовка `X-Studio-Client` (`api/deps.py`); редактор шлёт `ui`, без заголовка `api`.
9. Фоновые циклы (планировщик, getUpdates, восстановление `sending` после падения) ведёт ровно один процесс: тот, кто держит lease `loops` в таблице `meta` (`services/loops.py`). При остановке планировщик не берёт новые посты, а начатые отправки (и опрос после поста, и первый комментарий) получают `SHUTDOWN_GRACE` секунд; оборванная отмена отправка помечается «мог уйти». Восстановление `sending` не трогает строки, подтверждение которых процесс помнит (`publisher.unrecorded`): сначала пробует их дописать. После аварийного перезапуска (lease не отдан) новый процесс берёт его, когда тот истечёт: до `LEASE_TTL` (60 с) планировщик и восстановление не работают. Продление lease, которое падает с ошибкой БД дольше `LEASE_TTL - RENEW`, переводит процесс в резерв, чтобы лидеров не стало два (срок считается по времени от последнего успешного продления). Ошибка не останавливает продление: когда БД оживёт, процесс снова возьмёт lease.
10. Замена содержимого поста (`edit`, кнопки) сначала берёт следующую `posts.version` (`store.claim_version`: один `UPDATE … RETURNING`, номер взятой версии приходит тем же запросом; нужен SQLite ≥ 3.35), потом идёт в Telegram: две правки одной версии не проходят обе, вторая получает 409. Отказ Telegram или студии возвращает версию (`store.release_version`); сетевая ошибка оставляет её занятой и отвечает «правка могла пройти». Замена и запись прежней версии в `post_versions` идут одной транзакцией.

## Куда добавлять новое

- Новый метод Bot API для постов: функция в `services/posts.py` + маршрут в `api/posts.py` + тест в `tests/`.
- Новый тип сообщения (как опрос или Live Photo): запись в `services/kinds.py` с проверкой, маршрут или инструмент MCP через `posts.send_kind`, диалог в редакторе. Отправка, планировщик, правка, кнопки и список постов берут остальное из записи.
- Новое событие от Telegram: ветка в `services/updates.handle_update` и тип в `ALLOWED_UPDATES`.
- Изменение схемы БД, новая колонка тоже: новый файл `store/migrations/NNNN_имя.sql` со следующим номером (старые не менять; `EXTRA_COLUMNS` закрыт). Номера идут подряд, повтор или пропуск останавливает запуск. Шаг выполняется в одной транзакции со своим номером, поэтому в файле не должно быть своих `begin`/`commit` и `vacuum`.
- Новое поле поста (`models.Post`): что оно хранит в терминах Bot API, `json_schema_extra=bot_api("Тип")`; по нему вкладка JSON подсказывает поля внутри, и его видно в OpenAPI. Без него подсказок внутри поля нет, это ловит `tests/test_api.py`.
- Новая настройка: поле в `Settings` + `from_env` (числа через `_number`, секреты через `_secret`: ошибка попадает в общий список) + строка в `.env.example`; обязательное на сервере — в `_server_problems`.
- Новый маршрут, который публикует или меняет канал: `dependencies=PUBLISH` (см. `api/posts.py`), опасный для всей студии — `Depends(need("admin"))`; тест в `tests/test_access.py`. Инструмент MCP получает уровень по своим аннотациям (`PUBLIC` — `publish`, только чтение — `read`, остальное — `draft`).
- Новый фоновый цикл: функция в списке `factories` в `main.lifespan` (запускается под lease, только в одном процессе) и строки по [OBSERVABILITY.md](OBSERVABILITY.md#куда-добавлять-новое).
- Новая проверка состояния, событие в журнале или фоновый цикл: [OBSERVABILITY.md](OBSERVABILITY.md#куда-добавлять-новое).

## Тесты

- `pytest` — API на фейковом Telegram (`tests/mock_telegram.py`, он же сервер для браузерных проверок). У каждого теста своя пустая папка данных, порядок тестов не важен. Фоновые циклы выключены (`STUDIO_BACKGROUND=off`); тест сам вызывает `scheduler.run_due_posts()` или `updates.handle_update()`.
- Ожидание в коде подменяется через `_sleep` модуля (`telegram.client`, `services.updates`), а не через `asyncio.sleep`: глобальная подмена останавливает фейковый сервер в соседнем потоке, и тесты зависают.
- Подменять настройки: `monkeypatch.setattr(settings.get(), "preview_chat", "")`.
- Подменять Telegram: `monkeypatch.setattr(telegram, "call", fake)`.
- `tests/e2e_ui.mjs` — раннер браузерных проверок против запущенной студии и `tests/mock_telegram.py`; сами проверки — по файлу на каждую в `tests/e2e/`.
- `npm run test:render` — `tests/render_unit.mjs`: очистка HTML/Markdown в render.js на враждебных примерах (script, on*, javascript:, svg, mXSS), без студии. Новая дыра в санитайзере → сначала пример сюда.
- `npm run test:codemirror` — `tests/codemirror_vendor.mjs`: вендоренный CodeMirror (`make vendor`, [0017](decisions/0017-codemirror-vendored-modules.md)) грузится в Node без DOM, каждый bare-импорт запрещён. `npm run test:completion` — `tests/completion_unit.mjs`: подсказки вкладок исходника (`static/js/completion.js`) через настоящий `CompletionContext` на спецификации, которую отдаёт `GET /api/spec` (типы с `const_field` и конверт поста `post`: поля `models.Post` с их `bot_api`, параметры sendRichMessage и sendPoll из `api/specs.py`).
- `npm run test:parity` — `tests/render_parity.mjs`: предпросмотр каждого примера из `tests/telegram_parse/captured.json` совпадает с предпросмотром блоков, которые для него вернул настоящий Telegram. Новый пример: добавить в `cases.json` и записать `scripts/capture_telegram_parse.py` (нужен токен и чат, сообщения сразу удаляются). Осознанное расхождение помечается `known_gap` с причиной.
- `npm run test:export` — `tests/html_export.mjs`: «В HTML» (`static/js/html-export.js`) на блоках настоящего Telegram из `captured.json` (через `spec/convert.py`, нужен Python студии) даёт HTML, который предпросмотр рисует как те же блоки; отказы перечисляют всё, что не попало бы в HTML.
- `npm run lint` — ESLint для `app/static` и тестов на JS: ловит неопределённые имена и забытые импорты, которые браузер покажет только при клике.
- Перед изменением и перед PR: `make check` (ruff, формат, mypy, `lint-imports`, pytest, ESLint, tsc, сверка вендора CodeMirror, `test:codemirror`, `test:completion`, `test:render`, `test:parity`, `test:shots`, `test:export`).
