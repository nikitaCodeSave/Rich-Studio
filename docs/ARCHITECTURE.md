# Как устроен код Rich Studio

Правило слоёв: **api / mcp_tools → services → telegram / store / spec**. Стрелки идут только вниз.

| Папка / файл | Что делает | Чего не делает |
|---|---|---|
| `app/cli.py` | токены доступа из командной строки (`make token`) | экрана для токенов в редакторе нет намеренно |
| `app/main.py` | `create_app()`: middleware, обработчики ошибок, роутеры, фоновые циклы | логики нет |
| `app/settings.py` | все переменные окружения в одном `Settings`; модули вызывают `settings.get()` в момент использования; проверка при старте (`SettingsError` со всеми ошибками сразу), секреты из `*_FILE`, правила `STUDIO_MODE=server` | не читает env при импорте других модулей |
| `app/security.py` | Host, CSRF, Content-Type, CSP; кто спрашивает (`Principal`: именной токен, `STUDIO_API_KEY` или cookie сессии редактора) и уровень по методу запроса (GET — `read`, остальное — `draft`) | уровни выше `draft` проверяют сами маршруты (`api.deps.need`) и инструменты MCP (`mcp_tools.common.level_of`) |
| `app/logs.py` | журнал: stderr для человека, JSON с ротацией в `DATA_DIR/logs` для агента, `request_id` на каждой строке (`bind`), вычистка токена, чтение с фильтрами | |
| `app/metrics.py` | счётчики, задержки p50/p95 и пульс фоновых циклов в памяти процесса; его можно звать из любого слоя | не пишет на диск |
| `app/errors.py` | `StudioError` (400), `NotFound`, `Invalid` (422), `Upstream` (502); `telegram.TelegramError` с кодом 400 → 422, прочие → 502 | |
| `app/models.py` | тела запросов (pydantic), описания полей на русском для /docs | |
| `app/api/*.py` | роутеры: разобрать запрос → вызвать сервис → вернуть результат | не ходят в Telegram напрямую, кроме `raw` (проверка канала идёт через `services.channels`) |
| `app/mcp_tools/` | MCP-сервер на `/mcp`: курированные инструменты для агентов поверх сервисов, тот же guard и ключ API | не дублирует логику сервисов; удаление постов и `/api/raw` сюда не выносятся; страница предпросмотра `ui://` собирается из `static/` (`preview_app.py`), а не пишется отдельно |
| `app/services/kinds.py` | типы сообщений (`rich`, `poll`, `live_photo`, `paid_media`): метод Bot API, где лежат параметры, подписи, можно ли заменить, где кнопки, проверка перед отправкой; описание для редактора в `/api/config` ([0013](decisions/0013-message-kinds-registry.md)) | тип не угадывается по содержимому: его берут из `posts.kind` |
| `app/services/publisher.py` | отправка (метод по типу из `kinds`), шаги после отправки, рассылка в несколько каналов, валидация, время | не импортирует FastAPI |
| `app/services/posts.py` | что можно сделать с постом: опубликовать, предпросмотр, отложить, заменить, закрепить, кнопки, удалить; опросы, Live Photo и платный контент отдельными сообщениями (`send_kind`) | |
| `app/services/channels.py` | каналы: название, форум и темы, права бота (из `getChat`/`getChatMember` при проверке); темы из событий `forum_topic_created`/`edited` | Telegram спрашивается только при проверке |
| `app/services/scheduler.py` | отложенные посты | |
| `app/services/loops.py` | фоновые циклы под lease в SQLite: их ведёт один процесс, второй ждёт в резерве; остановка без обрыва отправок | |
| `app/services/updates.py` | getUpdates: нажатия, первый комментарий, реакции, опросы, вступления по ссылкам, предложенные посты и их исходы; `STATUS` | |
| `app/services/invite_links.py` | именные пригласительные ссылки и платная подписка (create/edit/revoke в Telegram), счётчики вступлений и заявок из `chat_member` / `chat_join_request` | Telegram эти счётчики боту не даёт: только то, что студия увидела сама |
| `app/services/suggested_posts.py` | предложенные посты из личных сообщений канала: что пришло (`suggested_post_info`), принять (`approveSuggestedPost`) или отклонить, исходы из служебных сообщений | публикует принятый пост Telegram, а не студия: в `posts` он не попадает. Решение занимает запись (`pending` → `approving`/`declining`) до запроса: второй клик не уходит, при отказе Telegram запись возвращается, при «могло дойти» ждёт служебного сообщения |
| `app/services/health.py` | отчёт о состоянии: проверки `ok/warn/fail` с подсказкой `action` | только читает |
| `app/services/housekeeping.py` | раз в 5 минут пишет смену статуса проверок в журнал, раз в час уборка | не удаляет сделанное человеком без `VERSIONS_KEEP` / `MEDIA_UNUSED_DAYS` |
| `app/services/media.py` | имена загрузок, путь внутри папки media, загрузка по ссылке (только публичные адреса, каждый редирект проверяется; через системный прокси, если он задан, ADR 0012), `used` и удаление ненужных файлов | |
| `app/services/listing.py` | как пост выглядит в списках: первая строка, миниатюра, ссылка t.me, подписи кнопок к нажатиям | только читает |
| `app/services/idempotency.py` | `run`: ключ повтора для всего, что публикует в канал (см. политику ошибок ниже) | |
| `app/services/backup.py` | бэкап: zip с базой и файлами, ежедневная копия базы | |
| `app/telegram/` | транспорт к Bot API, `upload:` → `attach://` (в полях файлов `media`, `photo`, `live_photo`, `thumbnail`, `cover`), проверка прав бота | не меняет payload, кроме `upload:` |
| `app/store/` | SQLite: соединения, миграции (`PRAGMA user_version`), черновики, посты, каналы | |
| `app/spec/` | загрузка и кэш api.json (с `SPEC_PIN` только копия из образа), сводка для редактора, diff версий, валидатор, перевод блоков из ответа Telegram в отправляемые (`convert.py`) | |
| `app/static/js/` | редактор: ES-модули без сборки, вход `main.js`; общее состояние в `state.js` | не пишет пользовательский HTML в `innerHTML` (это запрещает ESLint) |
| `app/static/render.js` | предпросмотр поста, очистка HTML/Markdown (`sanitize`), разбор HTML/Markdown по правилам Telegram, `outline` для сверки | правила разбора меняются только вместе с примером в `tests/telegram_parse/`, записанным с настоящего Telegram |

## Сервер

`deploy/`: студия в образе из GHCR (uid 10001, read-only), Caddy с HTTPS, Litestream с копией базы в S3. Образ собирает `.github/workflows/image.yml` по ручному запуску или тегу `v*`, пакеты из `requirements.lock` с хэшами. Восстановление из реплики проверяет `scripts/restore_check.sh` (CI `restore.yml`, ежедневно). Решение: [0010](decisions/0010-server-image-and-pinned-spec.md).

## Политика ошибок при отправке

1. Строка поста пишется со статусом `sending` **до** вызова Telegram (и для немедленной отправки, и для отложенной). Если процесс умрёт между ответом Telegram и записью, строка останется, и следующий старт пометит её «мог уйти». Не получилось записать строку — в Telegram ничего не уходит. Отправка прошла → пост записан как `sent`. Всё, что после (закреп, комментарий, опрос `poll_after`), только добавляет предупреждения. Опрос после поста записывается отдельной строкой `kind=poll` (`sent` или `failed`); при сетевой ошибке его, как и пост, не повторяют.
2. Сетевая ошибка во время отправки, ответ 5xx или страница ошибки шлюза (`telegram.NoAnswer`) → «пост мог уйти, проверьте канал». Автоматического повтора нет. Повторять можно только то, что точно не ушло: `telegram.Unreachable` (соединение не установлено) и 429; планировщик возвращает такой пост в очередь (`retry_at`). Отложенный пост, опоздавший больше `SCHEDULE_LATE_MIN` (сервис был выключен), не отправляется, а получает статус `missed`.
3. Один канал упал → остальные всё равно отправляются. Неудачная отправка (отказ Telegram или «мог уйти») записывается постом со статусом `failed` и текстом ошибки: её видно во вкладке «Посты» и в `list_posts`. Успешная отправка того же черновика в тот же канал убирает его прежние отказы; записи «мог уйти» остаются (в канале может быть дубль). `DELETE` убирает неудачную запись вручную. Отказ Telegram с кодом 400 отдаётся как 422 (запрос плохой, повтор не поможет), остальные ошибки Telegram как 502.
4. Предпросмотр уходит только в `TG_PREVIEW_CHAT` или в явно указанный chat_id, никогда в канал по умолчанию. Публикация без chat_id уходит в каналы черновика (`drafts.chat_ids`), а если их нет, в канал по умолчанию.
5. `Idempotency-Key` (`services/idempotency.py`, таблица `idempotency`): повтор с тем же ключом возвращает первый результат; если первая попытка закончилась `MayHaveGone`, повтор получает ту же ошибку; если ничего не ушло, ключ освобождается.
6. Замена опубликованного поста (`posts.after_edit`) меняет в записи только текст и кнопки; ответы на кнопки и первый комментарий остаются, если новый пост не принёс свои. «message is not modified» от Telegram не ошибка.
7. Каждая замена поста через студию (`posts.edit`, `posts.edit_message`, `posts.set_buttons`) сначала кладёт прежнее содержимое в `post_versions`. Отложенный и пропущенный пост заменяется только пока он ждёт (`status in ('scheduled', 'missed')` в том же `UPDATE`): взятый планировщиком уходит с тем, что было. Редактор передаёт `post_version` прочитанного поста, при 409 показывает, что пост изменили, и заменяет только после подтверждения.
8. Кто отправил пост, пишется в `posts.actor` из заголовка `X-Studio-Client` (`api/deps.py`); редактор шлёт `ui`, без заголовка `api`.
9. Фоновые циклы (планировщик, getUpdates, восстановление `sending` после падения) ведёт ровно один процесс: тот, кто держит lease `loops` в таблице `meta` (`services/loops.py`). При остановке планировщик не берёт новые посты, а начатые отправки получают `SHUTDOWN_GRACE` секунд; оборванная отмена отправка помечается «мог уйти». После аварийного перезапуска (lease не отдан) новый процесс берёт его, когда тот истечёт: до `LEASE_TTL` (60 с) планировщик и восстановление не работают. Продление lease, которое падает с ошибкой БД дольше `LEASE_TTL - RENEW`, переводит процесс в резерв, чтобы лидеров не стало два (срок считается по времени от последнего успешного продления). Ошибка не останавливает продление: когда БД оживёт, процесс снова возьмёт lease.
10. Замена содержимого поста (`edit`, кнопки) сначала берёт следующую `posts.version` (`store.claim_version`: один `UPDATE … RETURNING`, номер взятой версии приходит тем же запросом; нужен SQLite ≥ 3.35), потом идёт в Telegram: две правки одной версии не проходят обе, вторая получает 409. Отказ Telegram или студии возвращает версию (`store.release_version`); сетевая ошибка оставляет её занятой и отвечает «правка могла пройти». Замена и запись прежней версии в `post_versions` идут одной транзакцией.

## Куда добавлять новое

- Новый метод Bot API для постов: функция в `services/posts.py` + маршрут в `api/posts.py` + тест в `tests/`.
- Новый тип сообщения (как опрос или Live Photo): запись в `services/kinds.py` с проверкой, маршрут или инструмент MCP через `posts.send_kind`, диалог в редакторе. Отправка, планировщик, правка, кнопки и список постов берут остальное из записи.
- Новое событие от Telegram: ветка в `services/updates.handle_update` и тип в `ALLOWED_UPDATES`.
- Изменение схемы БД, новая колонка тоже: новый файл `store/migrations/NNNN_имя.sql` со следующим номером (старые не менять; `EXTRA_COLUMNS` закрыт). Номера идут подряд, повтор или пропуск останавливает запуск.
- Новая настройка: поле в `Settings` + `from_env` (числа через `_number`, секреты через `_secret`: ошибка попадает в общий список) + строка в `.env.example`; обязательное на сервере — в `_server_problems`.
- Новый маршрут, который публикует или меняет канал: `dependencies=PUBLISH` (см. `api/posts.py`), опасный для всей студии — `Depends(need("admin"))`; тест в `tests/test_access.py`. Инструмент MCP получает уровень по своим аннотациям (`PUBLIC` — `publish`, только чтение — `read`, остальное — `draft`).
- Новый фоновый цикл: функция в списке `factories` в `main.lifespan` (запускается под lease, только в одном процессе) и строки по [OBSERVABILITY.md](OBSERVABILITY.md#куда-добавлять-новое).
- Новая проверка состояния, событие в журнале или фоновый цикл: [OBSERVABILITY.md](OBSERVABILITY.md#куда-добавлять-новое).

## Тесты

- `pytest` — API на фейковом Telegram (`tests/mock_telegram.py`, он же сервер для браузерных проверок). У каждого теста своя пустая папка данных, порядок тестов не важен. Фоновые циклы выключены (`STUDIO_BACKGROUND=off`); тест сам вызывает `scheduler.run_due_posts()` или `updates.handle_update()`.
- Ожидание в коде подменяется через `_sleep` модуля (`telegram.client`, `services.updates`), а не через `asyncio.sleep`: глобальная подмена останавливает фейковый сервер в соседнем потоке, и тесты зависают.
- Подменять настройки: `monkeypatch.setattr(settings.get(), "preview_chat", "")`.
- Подменять Telegram: `monkeypatch.setattr(telegram, "call", fake)`.
- `tests/e2e_ui.mjs` — раннер браузерных проверок против запущенной студии и `tests/mock_telegram.py`; сами проверки — по файлу на каждую в `tests/e2e/`.
- `npm run test:render` — `tests/render_unit.mjs`: очистка HTML/Markdown в render.js на враждебных примерах (script, on*, javascript:, svg, mXSS), без студии. Новая дыра в санитайзере → сначала пример сюда.
- `npm run test:parity` — `tests/render_parity.mjs`: предпросмотр каждого примера из `tests/telegram_parse/captured.json` совпадает с предпросмотром блоков, которые для него вернул настоящий Telegram. Новый пример: добавить в `cases.json` и записать `scripts/capture_telegram_parse.py` (нужен токен и чат, сообщения сразу удаляются). Осознанное расхождение помечается `known_gap` с причиной.
- `npm run lint` — ESLint для `app/static` и тестов на JS: ловит неопределённые имена и забытые импорты, которые браузер покажет только при клике.
- Перед изменением и перед PR: `make check` (ruff, формат, mypy, `lint-imports`, pytest, ESLint, tsc, `test:render`, `test:parity`, `test:shots`).
