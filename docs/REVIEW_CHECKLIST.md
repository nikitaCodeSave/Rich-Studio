# Чек-лист ревью Rich Studio

Каждый PR (или каждое изменение общей папки) проходит этот список. Пункт «не применимо» — нормально, пропуск без причины — нет.

## 1. Главное обещание продукта
- [ ] Payload уходит в Bot API **как есть**. Никаких переименований полей, «улучшений» и вырезания незнакомого. Единственная перезапись — `upload:<файл>` → `attach://`.
- [ ] Незнакомое поле или тип — **предупреждение**, не ошибка. Свежая фича Telegram не должна блокироваться устаревшей спецификацией.
- [ ] Новый UI-элемент берёт данные из спецификации (`/api/spec`), а не захардкожен. Если захардкожен (русские подписи, сниппеты, рендер), это записано в README → «Что поддерживается вручную».

## 2. Нельзя опубликовать не туда и нельзя опубликовать дважды
- [ ] Любой путь отправки знает точный chat_id. Нет молчаливых фолбэков на канал по умолчанию там, где пользователь ждёт личку.
- [ ] После успешного `send*` пост **в любом случае** записан как `sent`. Ошибки «после отправки» (закреп, комментарий, БД) — предупреждения, не `failed`.
- [ ] Сетевая ошибка при отправке → сообщение «пост мог уйти, проверьте канал», без автоматического повтора.
- [ ] Рассылка в несколько каналов: сбой одного канала не останавливает остальные.

## 3. Ошибки
- [ ] Нет голых `except Exception` без записи в лог или в поле `error`.
- [ ] `HTTPException` только в слое API. Сервисы и фоновые циклы бросают свои ошибки.
- [ ] Ошибка пользователя → 4xx с понятным русским текстом. Отказ Telegram (400) → 422, прочие ошибки Telegram → 502, в обоих случаях с `description`.
- [ ] Фоновые циклы (планировщик, getUpdates, спецификация) не могут умереть от исключения.

## 4. Безопасность (локальный сервис, но всё равно)
- [ ] Новый маршрут под guard: Host, CSRF (`Sec-Fetch-Site`/`Origin`), `X-API-Key`. Исключения из авторизации только для статики и `/healthz`.
- [ ] Пользовательский HTML/Markdown рисуется только через `sanitize()` в render.js. В `static/js/` нет `innerHTML` с данными.
- [ ] Пути к файлам проверяются через `resolve()` + «внутри MEDIA_DIR».
- [ ] Токен бота не попадает в логи, ответы API, сообщения об ошибках, тесты, коммиты.
- [ ] Новый «опасный» метод Bot API (удаляет, банит, меняет вебхук) требует `X-Confirm: yes` в `/api/raw`.
- [ ] SQL только с параметрами `?`. Имена колонок — из белого списка.

## 5. Данные
- [ ] Новая колонка — через миграцию (`EXTRA_COLUMNS`, позже `PRAGMA user_version`), старая БД пользователя продолжает работать.
- [ ] Соединения SQLite закрываются (`with store.conn()`).

## 6. Тесты
- [ ] Баг-фикс приходит с тестом, который падал до исправления.
- [ ] Новая фича — тест API на фейковом Telegram (`tests/`). Изменение UI — проверка в `tests/e2e/` (новый файл).
- [ ] Тест не зависит от порядка и от фонового планировщика (вызывает `run_due_posts` сам).
- [ ] Никаких реальных сетевых запросов и реального токена.
- [ ] `ruff check`, `ruff format --check`, `mypy`, `pytest`, `npm run lint`, `npm run test:render` зелёные.

## 7. Документация и скилл
- [ ] Новая возможность описана в README и, если ею будут пользоваться агенты, в `.claude/skills/telegram-rich-posts/SKILL.md`.
- [ ] OpenAPI-описание маршрута (summary, описания полей) на русском и понятно агенту без чтения кода.

## 8. Размер изменения
- [ ] PR делает одну вещь. Рефакторинг и новая фича — разные PR.
- [ ] Дифф читается за 15 минут. Больше — разбить.

## 9. Несколько агентов параллельно
- [ ] Дифф не выходит за пути, объявленные в задаче; если вышел, в PR сказано почему.
- [ ] Ветка свежая относительно `main` (rebase), после rebase `make check` снова зелёный.
- [ ] Новая миграция — новый файл в `app/store/migrations/`, старые не изменены, `EXTRA_COLUMNS` не тронут.
- [ ] Сгенерированные файлы (`docs/openapi.json`, `docs/reference/`) пересобраны после rebase (`make docs`), а не слиты руками.
- [ ] Ревью делает не автор: отдельный агент с этим списком; PR, которые трогают `security.py`, `api/raw.py`, `services/media.py`, `render.js`, Dockerfile или CI, дополнительно смотрит ревьюер безопасности.
